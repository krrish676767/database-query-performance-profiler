# Requirements Specification - Database Query Performance Profiler

**Course:** PES University - Dept. of CSE  
**Lab:** Lab 1: Requirements Engineering & UML Use-Case Modelling  
**Problem Statement #44:** Developer Tools & IT Operations - Database Query Performance Profiler  
**Target Stakeholders / Actors:** Database Administrator (DBA), Backend Lead  

---

## 1. Functional Requirements (FR-001 to FR-005)

| Requirement ID | Requirement Type | Description | Priority | Acceptance Criteria | Rationale |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **FR-001** | Functional | The system shall parse PostgreSQL and MySQL `EXPLAIN` (JSON/TEXT) execution plans, detect high-cost execution nodes (such as sequential table scans on tables exceeding 100,000 rows), and automatically recommend optimal single or composite index column definitions. | **High** | **Pass:** System correctly identifies missing composite index on filtered columns (`WHERE`/`JOIN`) and generates index definition.<br>**Fail:** Query execution plan containing unindexed sequential scan on large table is marked as optimized. | Automated execution plan parsing eliminates manual log analysis, enabling DBAs and Backend Leads to prevent full table scans that degrade host database performance. |
| **FR-002** | Functional | The system shall continuously ingest slow query log streams (from PostgreSQL `pg_stat_statements`/slow query log and MySQL slow query log) via log tailing or HTTP API ingestion, normalizing literal query parameters into parameterless query fingerprints. | **High** | **Pass:** Raw query strings are parsed into standardized query signatures without sensitive literal data within 2 seconds of log emission.<br>**Fail:** Ingestion queue drops log batches under load or retains sensitive PII/literal constants in query fingerprints. | Query fingerprinting aggregates duplicate execution instances safely without exposing sensitive production data or PII in logs. |
| **FR-003** | Functional | The system shall generate automated weekly performance optimization digests summarizing top 10 slowest query patterns, cumulative execution time impact, index recommendations, and performance trend graphs, dispatching notifications to the Backend Lead and Database Administrator. | **Medium** | **Pass:** Weekly digest report is compiled on a scheduled 7-day interval and delivered via email/Slack containing actionable index suggestions.<br>**Fail:** Digest fails to execute automatically or omits queries executed during the 7-day reporting period. | Periodic digests provide engineering leadership with proactive observability and actionable insights without requiring continuous log monitoring. |
| **FR-004** | Functional | The system shall provide an interactive web dashboard for Database Administrators and Backend Leads to filter query metrics by execution duration, frequency, database instance, and index severity, with one-click export of SQL `CREATE INDEX` DDL statements. | **Medium** | **Pass:** Users can filter query metrics across multiple dimensions and copy valid `CREATE INDEX` DDL statements.<br>**Fail:** Dashboard filters produce invalid SQL DDL or fail to respond within 3 seconds when querying 100,000 recorded execution entries. | Direct export of validated `CREATE INDEX` DDL statements accelerates schema remediation and reduces human error during production database migrations. |
| **FR-005** | Functional | The system shall allow Backend Leads to configure custom performance alert thresholds (e.g., query execution time > 500ms, CPU utilization > 80%, or > 50 sequential scans/min) and dispatch real-time alert notifications via Slack, Webhooks, or Email. | **High** | **Pass:** Alert notification is dispatched within 30 seconds when an ingested query breaches the configured threshold.<br>**Fail:** System fails to trigger an alert upon threshold breach or dispatches duplicate alerts for a single event. | Real-time alerts empower engineering teams to address critical database bottlenecks before they cause cascading service downtime or customer-facing latency. |

## 2. Non-Functional Requirements (NFR-001 & NFR-002)

| Requirement ID | Requirement Type | Description | Priority | Acceptance Criteria | Rationale |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **NFR-001** | Performance & Security | Slow query log ingestion must handle up to 5,000 log records per minute without dropping entries, exceeding 50ms processing latency per record, or placing more than 1% CPU overhead on the host database server, while encrypting log data at rest using AES-256. | **High** | **Pass:** Benchmarking tests confirm target throughput (5,000 logs/min) and processing latency (< 50ms) with zero dropped records and AES-256 encryption at rest under peak load.<br>**Fail:** Ingestion queue drops records under peak load or transmits/stores log data over unencrypted channels. | High-throughput log ingestion must operate asynchronously and securely to ensure the observability tool itself does not degrade production host database performance or violate security standards. |
| **NFR-002** | Usability & Availability | The web application dashboard must maintain 99.9% uptime during operational hours and render query execution plan visualizations within 1.5 seconds for datasets containing up to 1,000,000 aggregated query events. | **Medium** | **Pass:** Dashboard page load and chart rendering complete within 1.5 seconds for 95% of requests under 50 concurrent user sessions, with system uptime monitoring reporting >= 99.9%.<br>**Fail:** Dashboard rendering takes > 3.0 seconds or monthly availability drops below 99.9%. | High availability and fast UI responsiveness ensure DBAs and Backend Leads can diagnose production performance bottlenecks without delay during critical incidents. |
